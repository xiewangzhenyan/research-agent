# 执行控制与 Jev 路由

LangGraph 统一负责持久执行、模型／工具节点、检查点和恢复；
langchain-openai 只适配 OpenAI Responses，Pydantic v2 负责参数与结构化结果校验。
PydanticAI 及 pydantic-graph 已移除。可选 Jev 是路线决策服务。

## 原生执行与迁移

外层持久图保留资料检索、信息完整性检查、审批与任务修订控制。
`app/agents/runtime.py` 的原生子图按“模型 → 单个工具 → 下一个工具／模型”执行，
每个已返回的工具结果都有独立检查点，继承父图的 PostgreSQL checkpointer。
执行器恢复时使用保存的消息与下一节点，不重跑已有结果的工具。
进程在工具外部副作用发生后、结果检查点提交前退出时，仍可能重试该工具；
文档、Python 与 MCP 继续使用各自已有的幂等键和派发记录，不能宣称通用 exactly-once。

`ToolRegistry` 仅负责把带类型的函数注册成原生 StructuredTool，不拥有调度循环。
模型和工具调用前重新校验当前资料／能力范围，工具仍单独检查操作许可与 worker fence。
同一模型回复同时包含澄清和其他工具时，只保留一个澄清，其他工具不执行。
澄清／MCP 审批交给外层 `await_input`，沿用原有持久恢复协议。

分类、检索改写、记忆提取和协作角色调用统一使用 `structured_call`：
只绑定一个结果 schema、强制结果工具、Pydantic 校验、有界重试，没有可执行业务工具。
模型自动重试关闭；超时、请求数、token、工具次数和上下文预算由应用显式控制。
流式文本、推理摘要、工具进度继续通过原有事件协议发送。

新检查点写入原生 LangChain 消息 JSON；`app/agents/messages.py` 只读转换旧消息 JSON，
支持文本、工具、待回答的澄清及二进制图片，不依赖旧运行时；未知格式明确失败。
原生执行器迁移本身保持 PostgreSQL 表结构和任务 API；下文产物检查另有 0049 数据库迁移。
切换代码需在批量发布时更新 API 与 worker，
并协调停止旧 worker，避免同一队列同时使用两种消息写入格式。

`tests/test_native_runtime.py` 覆盖重建父子图后的工具恢复、旧消息、预算与取消；
设置 `RUN_TASK_DB_TESTS=1` 后会同时使用独立 PostgreSQL 验证工具检查点恢复。

## 五项设计的落地（2026-10-27）

| 设计 | 当前实现 |
| --- | --- |
| 统一 Agent 工厂 | `agents/factory.py` 的 `AgentDefinition` 保存角色提示、输出 schema 与预算；主 Agent 和规划／研究／撰写／审校角色共用 `create_agent`。工厂只装配，执行仍由原生图及模型调用负责。 |
| 集中执行策略 | `agents/policy.py` 按“重新验证范围 → 用量与上下文预算 → 循环检查 → 模型／工具执行”的顺序处理。响应阶段检查用量并优先澄清；仅输入错误转为工具重试，权限和服务错误继续传播。 |
| 独立业务状态 | `WorkContextSnapshot` 从现有 WorkTask、要求版本、步骤与产物记录重建。保存完整历史要求、最多 10 条步骤与 10 个文件引用；当前完整输入由消息 ID 关联。权限／要求／历史结果／产物变化会使旧上下文失效，单纯进度变化不会改变目标。 |
| 隔离与交接 | 每个协作角色只接收白名单字段；不传主聊天历史、记忆、能力配置或检索内部向量。研究员与撰写员返回 `RoleHandoff`，含原文引用对应的来源 ID、版本及代码设置的校验状态；审校结果单独交接。 |
| 渐进加载 | 只绑定 Skill 时只提供技能读取工具；只绑定 MCP 时只提供连接描述／调用工具。目录保留简介，正文与具体 schema 继续按需读取，原有精确参数审批与派发记录保留。 |

角色预算可以被调用方收紧，不能突破角色定义的上限。普通执行沿用最多 12 次模型请求，
带必要信息检查的任务沿用总计 18 次预算；协作角色不会取得可执行业务工具。
改写、分类等辅助调用也使用同一执行策略，但仍保留各自的输出合同与超时。

WorkTask 继续把用户原文与来源哈希作为要求依据，不让模型改写后覆盖用户目标；
聊天压缩不删除这些业务记录。源消息删除或改变时仍停止执行，不通过副本恢复已删除内容。
旧格式任务上下文按原有要求／历史结果检查；新格式还检查文件引用。产物列表只含
已完成执行的文件元数据，不复制文件正文，也不把文件存在视作用户验收。

研究角色只接收任务要求和版本，不接收步骤记录、历史回复或文件清单。
撰写员接收校验后的研究交接，避免同时重复传入整段研究摘要。
交接中的 `source_quotes_checked` 仅表示原文匹配与数字检查通过；
`review_approved` 表示当前审校角色通过，二者均不等同于事实已独立验证。
当前研究角色不生成文件，`artifact_ids` 保持空列表，避免模型编造产物引用。
已有检查点缺少交接字段时沿用历史摘要，后续节点补写新交接。

## 任务文件续用（2026-10-27）

启用 Python 且沙箱支持文件协议 2 时，主 Agent 会看到当前 WorkTask 清单中可计算文件的
ID 和只读路径。`run_python(code, artifact_ids=[...])` 显式选择之前已完成执行的文件，
支持 CSV、JSON、TXT、Markdown 和 PNG/JPEG。未选择的历史文件不读取、不传给沙箱；
Office 和 PDF 不作为本功能的输入。该能力沿用现有 Python 开关与权限，无需新增 API 字段。

执行前从业务记录重建任务范围并对比检查点快照，验证账号、项目、任务要求及当前修订；
所选文件必须出现在同一任务的既有产物清单中。旧修订产物可以明确选择，但保留
`historical` 标记，必须按当前要求重新检查。被替换目标之前的产物不会重新进入可用清单。
文件删除、元数据变化或内容 SHA-256／长度不匹配会阻止计算；上传附件与历史产物合计
最多 5 个、5 MiB，单个历史产物最多 2 MiB。源文件字节只在调用时加载，
事件和工具结果只保留 ID、名称、大小、哈希等元数据，不将 base64 正文写入检查点。

挂载名称包含文件 UUID，避免不同执行中同名文件互相覆盖；代码与实际输入字节继续
共同决定沙箱幂等键。跨会话续做由 WorkTask 业务记录重建文件引用，不依赖聊天摘要。
权限与快照校验在每次实际工具调用前进行，已完成工具节点仍沿用原生图的恢复规则。
这里验证的是输入完整性和来源范围，不代表文件内容正确，也不代表用户验收通过。

## 产物基础检查与验证记录（2026-10-27）

`RunArtifactService.save` 在落库前对整批文件运行有界、只读检查，任何一个文件失败，
整批均不保存。大小和 SHA-256 按实际字节重算；UTF-8 文本检查编码，JSON 检查语法
与最多 128 层嵌套，CSV 使用严格引号解析。超出 Python CSV 字段读取上限时保留
`not_checked` 和明确原因，不修改全局解析器限制，也不把未解析文件标为格式已检查。
空 CSV、合法多行字段和不等长行仍可保存，格式检查不规定业务表格 schema。

DOCX／XLSX／PPTX 检查 ZIP 条目、CRC、XML 及主文档部件声明和入口关系；
最多 2048 个条目、解压合计 16 MiB，不解包到磁盘，不执行 Office 或获取外部资源。
这些是包结构基础检查，不验证排版、全部 Office 语义或正文保真。
PNG／JPEG／PDF 当前只记录字节完整性，结构为 `not_checked`。

代码生成 `artifact-check-v1` 报告，包含绑定的文件哈希、大小、实际检查项和结构状态；
`content_validation` 始终为 `not_verified`。模型或上游传入的同名报告被忽略。
报告通过 **0049_artifact_validation** 迁移保存在产物记录中，在文件列表、工具结果和
WorkTask 上下文中恢复。旧记录默认 `{}`，任务上下文把它视作未检查，不推断通过；
旧检查点的文件引用不会因新增空检查字段而失效。

文档工具和 Python 工具收到可修正的文件格式错误时，使用现有预算让模型修改后重试；
权限、服务错误、来源删除和任务版本失效不归为此类文件错误。相同代码仍复用原沙箱
执行结果，修正代码产生新的执行标识。直接下载聊天回答也经过同一检查器。
最终是否满足研究目标、计算是否正确及用户是否验收，继续与文件格式检查分开。

发布时先应用 0049 迁移，再协调更新 API 和 worker；本地验证不修改生产数据库。

## 自动选择执行路线

只有已授权知识库、严格资料模式、无附件且未限定文档的请求，才有资格选择
`standard` 或 `knowledge_collaboration`。不符合范围的请求直接走原流程。
知识协作继续使用已有的规划、研究、撰写、独立审校流程及最多一次返工限制。
路线选择不改变知识范围、模型、工具许可、任务修订或引用校验。

可选 TypeSafe Jev 使用官方 `POST https://api.typesafe.ai/v1/systemone`，
以一个 Choice 返回 `standard`、`knowledge_collaboration` 或 `none`。
生效模式下不再依赖关键词筛选，因此不同措辞的复杂请求也能被识别。
`none`、低置信度、缺密钥、超时、429、服务错误或响应格式错误，均回退原路由。
原路由保留关键词筛选和有界生成模型判断，不把 Jev 故障当作任务失败。

| 配置 | 默认 | 用途 |
| --- | --- | --- |
| `JEV_ROUTING_MODE` | `off` | `off` 不调用；`shadow` 比较但不改变路线；`active` 应用达到阈值的选择 |
| `JEV_API_KEY` | 空 | 独立服务密钥；不会复用生成模型密钥 |
| `JEV_MODEL` | `jev-1.14.0` | 固定版本，升级后重新评估 |
| `JEV_TIMEOUT_SECONDS` | `2` | 整次调用期限，允许 0.1–5 秒，无自动重试或重定向 |
| `JEV_MIN_CONFIDENCE` | `0.8` | 应用选择的门槛，允许 0.5–1 |

配置在后端受 Git 忽略的环境文件中。重新创建使用该文件的 API / worker 容器后
才会影响运行服务；修改配置文件本身不会更新已启动容器。

Jev 只接收当前问题与已解析的检索问题，不接收整个对话、附件正文、项目记忆、
检索片段或密钥。两段问题合计超过 8,000 字符时跳过，不截断目标进行判断。
有长期任务完整要求时沿用原路由，避免只凭最新一句话误判整个任务。
解析后的问题可能包含用于消解追问的上下文信息，启用前应理解这是一次外部服务调用。

决策记录沿用 `routing_selected` 事件及 run 的 `routing` 字段，并随检查点保留。
记录模式、实际模型版本、置信度、概率分布、耗时、用量、回退原因及与原路线的分歧，
不保存服务错误正文。Jev 的置信度是选择分布的确定程度，不是任务成功率。
影子模式仍会产生外部调用费用和至多配置期限的额外等待。

## 重复工具结果保护

参考 DeerFlow 的循环检测和 WeKnora 的停滞保护，
`RepeatedToolResultGuard` 在每次模型调用前读取已有完整消息。
最近 12 个工具结果中，同一工具、同样参数和同样结果出现三次时停止本轮。
正常的工具结果变化不计作同一次重复；新用户消息和已回答的澄清重置观察窗口。

检测从持久消息重建，不依赖进程全局计数，适用于本轮检查点与澄清恢复。
停止后 run 为失败并展示明确的重复结果提示，不将截断的执行标记为成功。
该保护覆盖持久执行图中的工具调用，不能中断一个尚未返回的远端工具，
也不替代工具超时、最多 20 次工具调用、模型请求和总 token 限制。
同样结果的工具确实需要反复查询时，应补充新要求后继续。

## 评估与开启顺序

人工中英文冒烟集为 `backend/evals/routing_v1.json`，包含简单问题、复杂交叉研究、
模糊请求、范围外请求及修改路由规则的指令。它只覆盖编排路线，不能评估答案正确性，
也不能代表真实用户分布。先跑冒烟，再在影子模式下用真实请求标注路线和任务结果，
根据误升级、漏协作、完成成本与延迟决定何时切换 `active`。

从 `/tmp` 执行以避免自动加载生产环境，显式环境文件只读取 `JEV_*`：

```bash
# 离线检查，不发请求
PYTHONPATH=/path/to/backend /path/to/backend/.venv/bin/python \
  /path/to/backend/scripts/evaluate_routing.py

# 真实调用，会产生服务费用；报告不包含问题原文和密钥
PYTHONPATH=/path/to/backend /path/to/backend/.venv/bin/python \
  /path/to/backend/scripts/evaluate_routing.py --live \
  --env-file /path/to/backend/.env --output /tmp/routing-report.json
```

报告分别统计原始选择准确率、接纳覆盖、接纳准确率、错误升级、漏协作、
回退次数、延迟和输入 token。回退不算模型正确作答，也不自动视为任务失败。
该脚本不调用生成模型、检索服务或业务数据库。
