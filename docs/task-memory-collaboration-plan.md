# 长期任务工作记忆与多 Agent 工具协作实施方案

状态：第一批已完成本地实现及验收；第二、三批仍为后续计划。2026-09-14 按用户最新优先级：先工作记忆，再工具协作，OCR 后移。尚未推送 GitHub、构建 Docker 镜像或发布。浏览器验收允许在本机编译前端，测试数据库与线上隔离。

## 第一批实际交付边界

- 新增迁移 `0047_work_tasks`：长期工作任务、来源消息修订、关联会话、单轮执行台账和任务操作事件。`AgentRun` 仍是一轮执行，`WorkStep` 现阶段一对一关联 run，尚未实现子步骤依赖图。
- 通过明确的“创建任务：…”或多动作交付请求建立任务；明确续做可恢复本会话的唯一未结束任务，新会话可恢复本项目唯一未结束任务。多个候选时返回简短澄清，卡片可明确选择。**当前识别是保守的中文规则，不是模型语义分类，也不保证理解所有自然语言需求变更。**
- 暂停、取消、标记完成和要求修改均在聊天提交事务中处理。控制回复不调用模型、不排队等待旧澄清、不受执行槽满额影响；控制消息仍保存到对话。要求修改先停止旧版本，再排队新执行；同任务跨会话执行也保持顺序。
- 乐观修订与幂等键处理两窗口冲突、重复发送；恢复审批、工具授权、模型调用、结果与文件保存检查任务有效性。外部已发生的操作不能由版本号撤回，沙箱取消仍等待远端确认。
- 每次组装完整有效要求并预留上下文预算；超预算明确拒绝或停止，不截断目标。补充至多三个既往执行的 600 字结果摘录，并标注未独立验证。严格资料问答排除这些旧回答，只使用授权知识来源作证据。
- 原始要求通过消息 ID、账号、项目、角色和内容哈希核验，不将删除或编辑前的要求另存为永远可信的副本。原始要求失效时需重新设定完整目标。Mem0 的长期事实机制保持独立。
- 聊天内折叠任务卡片展示状态、要求版本、最近 10 次执行与 20 个文件；列表仅取近期 20 项，详情按需请求，运行中每 5 秒同步，不随每次流式刷新重取全部详情。卡片支持续做、追加修改、完整替换、暂停、取消与显式标记完成。无独立后台任务页面或执行模式选择器。
- **本轮回答完成不等于任务验收完成。** 本批记录真实执行状态，独立 Verifier、自动依赖检查、角色消息总线与并行工具协作尚未交付。
- 文件仍存于现有 run 产物服务，卡片提供有权限的下载入口。本批不自动将过去的附件／产物挂载到后续沙箱，也不把完整旧文件塞入上下文；文件交接属于第二批。删除来源会话后，该会话的结果／文件会被删除，任务保留失效状态或其他仍有效的来源。
- 每项目最多 20 个未结束任务；无永久绑定的用户沙箱，单轮执行仍遵守已有超时和恢复期限。长期业务状态不随 checkpoint 清理消失。

下述架构描述中超出以上范围的内容，仍是第二、三批的设计目标。

## 现有基础与实际缺口

- `AgentRun` 当前对应一次消息执行，已保存请求、状态、有效配置、结果和递增事件。
- `app/worker/agent_runs.py` 使用 PostgreSQL LangGraph checkpoint、advisory lock 和 attempt fence 恢复执行；已有 `interrupt` / `Command(resume=...)` 澄清流程。中断中的模型调用可能重做。
- 同会话请求按顺序处理，等待澄清时后续请求排队。执行中的需求变更必须新增控制路径，不能简单作为普通消息排在旧任务后面。
- `knowledge_collaboration.py` 已实现规划、研究、撰写、审校，最多返工一次，有独立节点检查点。当前限定知识库资料协作，不是通用的并行工具 Agent 系统。
- 已有远程 Python 沙箱客户端、只读输入、产物校验、幂等执行标识和取消确认；不在业务服务器执行生成代码。实际开放仍取决于账号权限和沙箱健康状态。
- Mem0 保存账号／项目下的长期事实；会话历史检索处理旧话题恢复。两者都不能替代任务的权威进度状态。

## 一、长期任务工作记忆

### 身份和状态

新增 `work_task` 表示持续多轮、跨日的工作目标；现有 `AgentRun` 继续表示一次有界执行。一个工作任务可以关联多个执行和对话；普通问答无需创建工作任务。同一会话可以讨论多个任务，不把整个会话永久绑定到一个目标。

第一阶段新增：

| 数据 | 保存内容 |
|---|---|
| `work_tasks` | 账号、项目、标题、当前版本、状态、事件序号与时间；要求及验收条件保留在来源消息中 |
| `work_task_revisions` | 来源消息 ID、内容哈希、版本及完整替换关系；不复制失效原文 |
| `work_steps` | 一轮执行的版本、run 关联、动作、真实状态／阶段及结果哈希；依赖与独立验证待第二批 |
| `work_task_events` | 有序控制／修订事件、幂等键与来源；详细执行事件保存在原 run 台账 |
| `work_task_conversations` | 已授权的会话关联与引用范围 |

约束采用服务端身份及复合外键／归属查询，不接受模型声明的账号或权限。关联会话必须属于同账号、同项目；默认项目也使用一致的内部作用域标识。账号知识库继续跨项目复用，读取每份资料时仍校验账号与本次授权范围。

业务状态保存在 PostgreSQL。Redis 只用于唤醒、缓存、限流等可重建数据；Redis 丢失后能够从数据库继续领取。LangGraph checkpoint 负责执行恢复，`work_task` 负责长期业务状态；旧 run checkpoint 的清理不能删除工作任务及其有效产物。

### 保存什么、如何更新

任务记录包含目标、明确约束、验收条件、决定、进度、阻塞、下一步、产物及其版本。数值、文件版本、验收条件采用结构化字段和来源引用，不能只保存一段不断覆盖的摘要。

- 新消息：第一批按保守规则判断继续／变更／新话题，明确选定任务时由服务端校验版本与归属；模型语义路由为后续增强。
- 工具完成：保存真实执行状态、日志引用和产物；不能根据 Agent 自述将工具标为成功。
- 子任务完成：记录产物和检查结果，检查通过后才满足依赖。
- 需求变化：追加新修订，分析受影响的依赖分支，保留未受影响的已验证结果。
- 阶段结束：生成便于阅读的简报。简报来自上述记录，重建简报不改变业务事实。
- 完成或归档：停止调度，按保存策略保留任务及产物。中间草稿不自动提升为 Mem0 的长期个人事实。

Mem0 仍按原有开关与事实提取规则工作；任务进度不通过向量相似度决定真伪。过期结果失效但保留审计；不因为某个决定近期很少被检索就自动删除它。用户删除或源文件撤销后，对应引用失效，后续执行重新检查依赖。

### 新消息与需求变更

明确的继续请求与唯一匹配任务自动衔接，并在聊天里显示当前任务名称。明确的新话题按普通聊天或新任务处理，不改旧目标。跨会话继续只恢复已匹配任务的结构化状态和授权来源，不灌入同项目全部聊天；存在多个同等匹配目标且会影响执行时，询问一次简短澄清。

执行中的取消、暂停、恢复、需求修订走独立控制路径，消息仍写入聊天记录，但不等待原有 FIFO 队列。控制写入与当前任务修订校验在事务中完成。普通聊天继续保留原有顺序语义。

例如用户把“比较三种方法并生成 Word”改为“只比较两种，输出 PPT”：

1. 记录原消息和新目标修订；已领取步骤带原修订号。
2. 停止派发旧方案中的受影响步骤；正在执行的步骤协作取消，沙箱停止需要远端确认。
3. 工具调用前与结果入账时校验修订、执行尝试和取消状态。迟到结果不能成为新方案的当前产物。
4. 仍适用的资料检索结果通过来源／版本检查后复用，重建受影响的比较和导出步骤。
5. 已经发生的外部操作无法由修订号撤回；记录实际结果，按工具契约决定补偿或提示用户。

接收用户新要求不必逐条弹窗确认；模型判断不等于事实保证。保留变更来源和可见任务概览，只有会改变关键目标的歧义才澄清。

### 长任务与上下文

“持续五天”表示状态可以保留和恢复，执行仍是有时限的步骤。等待用户或资源时释放 worker 和沙箱；工作任务生命周期与单次执行超时／重试次数分开，不通过无限延长一次调用实现长任务。

每次恢复按预算装配：当前要求、有效目标修订、关键约束、未完成步骤、必要产物／资料、相关近期消息。保留决定的原始来源，历史摘要只帮助检索。超预算时缩减辅助材料或拆步骤；不能静默截去用户关键要求。后续推进不依赖模型记住五天的全部对话。

## 二、多 Agent 工具协作

### 编排方式

LangGraph 继续作为唯一流程调度层，PydanticAI 承担角色模型调用、结构化输出和工具协议，Mem0 承担长期记忆。当前阶段不再引入第二个具有独立生命周期的调度框架。

采用协调者调度有界的依赖图。普通问题保留单 Agent＋Tools；只有存在独立子问题、异构工具需求或有价值的独立验证时进入协作。用户不需要选择执行模式。模型生成的依赖图必须经过环检测、步骤数、工具范围和预算校验；只调度已满足依赖的节点。

角色按任务按需创建：

| 角色 | 职责 | 默认权限 |
|---|---|---|
| Planner／协调者 | 拆解、调度、修订、合并、停止 | 读取工作状态，不直接执行任意代码 |
| Researcher | 检索资料，交付有来源的发现 | 已授权知识库检索 |
| Coder | 数据处理、计算、生成可验证产物 | 已授权只读输入及 Python 沙箱 |
| Verifier | 运行检查并核验结果／引用／约束 | 独立检查工具；不修改验收条件 |
| Writer | 整理已验证结果，生成报告 | 读取已接受的结果、受限文档导出 |

SQL、REST、网页搜索和可扩展技能只在各自工具契约、权限、超时及审计完成后接入，不能为了“多 Agent”直接给角色任意网络或数据库访问权。科研场景只是测试例子，流程同样适用于一般资料比较和数据分析。

### 角色通信和隔离

模型提出任务或结果，服务器将其包装为有类型的消息。建议字段：消息 ID、工作任务 ID、子任务 ID、发件／收件角色实例、类型、目标修订、关联输入、结果／产物引用、幂等键。类型限制为任务、发现、结果、变更建议、阻塞和取消等；发送者和作用域由服务器填入。

消息和调度事件在 PostgreSQL 事务中持久化，可由可领取事件表或 outbox 派发；Redis 通知丢失时数据库扫描补发。采用至少一次投递＋消费者幂等，不宣称消息或外部模型调用恰好一次。

每个角色实例有独立执行／checkpoint 和上下文，只能看到子任务目标、必要约束、被分配的资料，以及明确交接的结果。协调者看到整体状态、依赖和摘要，按需授权读取证据。各角色不互相读取完整聊天、私有思考或全部项目记忆。大文件通过带权限的产物 ID 交接，不复制进每个提示词。

所有当前状态由协调者按版本条件提交；角色只提交结果或变更建议。工作状态修订、派发事件和结果接收保持事务一致；checkpoint 与业务结果之间用稳定步骤 ID 和领取尝试对账，恢复后先查已接受结果，再决定是否重新调用模型。

### 并行、预算和停止

第一版最多同时运行两个独立子任务，随后根据实际吞吐调整；角色数量不等于并发数量。计算步骤服从沙箱服务更低的实际容量，1c1g 节点起步只允许一个 512 MiB 计算任务，若节点实测不足则降低额度或关闭该能力。等待计算时不占用常驻专属沙箱。

同一工作任务建立共享用量账本：调用前预占、完成后结算，跨角色合计模型调用、工具调用、输入／输出估算和实际返回用量。共享限制不能用每个角色各自计数替代。供应商可能忽略输出上限或不能准确上报失败用量，因此应用预算是派发和继续执行的边界，不承诺精确的预付费硬封顶；必要时提前停止并保留未完成项。

停止条件必须由代码执行：依赖图无环、最大步骤数、最大派生深度、总时长、总调用量、每步骤重试数及返工次数。初始返工最多两轮；相同输入版本反复产生相同失败原因且没有新证据时提前停止，提交阻塞原因或询问用户。角色不能自行无限生成下级角色、互相转派或修改停止条件。

冲突处理按来源、版本、确定性检查和原始验收要求进行。Verifier 不能仅凭文字判断推翻可重复计算，也不能偷偷放宽用户要求。缺乏依据的冲突保留到最终说明，影响关键交付时使用 `interrupt` 澄清，不能用“多数 Agent 同意”代替证据。

计算结论附输入版本、代码哈希、执行结果和检查记录；知识库结论附原文引用。两类依据分别标注，不能把计算推导伪装成文献原话。

### 工具执行和沙箱

在现有远端协议上增加角色步骤身份和稳定的逻辑调用标识。先保存工具调用意图，再调用远端；结果按账号、任务、子任务、输入版本和调用 ID 对账。幂等键覆盖逻辑调用、代码／参数、输入哈希和运行环境版本；传输重试复用同一调用，用户明确要求重新运行则创建新调用。

每次计算使用隔离临时环境，只读输入来自已授权产物，输出校验后保存到产物服务，计算结束释放容器。下个步骤通过显式挂载输入复用文件，不继承前一个容器的隐含内存或可写目录。保留网络禁用、CPU／内存／时长／文件数／磁盘／日志限额及取消确认；重新核对运行时健康，不因代码中写着 gVisor 就认定部署已满足。

纯计算、只读检索与受限文件生成可自动执行。后续具有外部写入效果的工具按已有授权范围执行；授权不足或关键输入缺失时，使用持久化 `interrupt`，以匹配的问题 ID 和修订恢复，避免普通回复误触发已过时审批。节点重入不会直接重放未对账的副作用；没有幂等和结果查询能力的外部写入不能盲目重试。

## 三、用户界面

沿用当前聊天页和“执行详情与文件”侧栏，不恢复独立后台任务页面。

- 长任务出现一张简洁卡片：目标、当前步骤、已完成／待完成、阻塞及产物。
- 默认只展示可理解的执行进展；展开后显示角色分工、检查结果、引用和文件版本，不展示私有思考。
- 用户直接发消息追加或修改要求；取消／暂停／恢复入口放在任务卡片，手机采用抽屉。
- 多任务并存时显示本条消息关联哪个任务；明确续做自动衔接，歧义时在聊天中澄清。
- 数据库任务事件是进展依据，页面刷新或关闭不拥有任务生命周期。新角色的消息按事件游标恢复，不重复添加气泡或文件。

## 四、实施批次及验收

1. **工作记忆与单执行路径接入**：表结构、任务关联、目标修订、步骤／产物账本、继续／变更／暂停控制路径、聊天任务卡片。普通问答回归通过后再启用。
2. **受控工具协作**：结构化计划、角色消息、独立子执行、共享预算、先串行跑通 Researcher → Coder → Verifier → Writer，再并行无依赖分支。复用原知识库协作，保留其严格引用模式。
3. **恢复和质量加固**：故障注入、重试／取消竞争、沙箱资源压力、真实中文任务效果评测，按账号逐步开放，按完整批次发布。

端到端验收示例：用户要求读取授权 CSV、比较方法并导出报告；中途改变比较范围，关闭网页，重启执行 worker，次日回到同一任务继续。系统保留新目标、复用仍有效的步骤、重算受影响结果，输出真实验证通过的文件；旧版本迟到结果不能覆盖新任务。

必须覆盖：账号／项目／会话越权、不同角色读错输入、两个浏览器同时修订、同一会话中断后的控制消息、Redis 通知丢失、worker 在调用前后崩溃、重复投递、工具运行中取消、源资料删除、旧检查点版本不兼容、预算并发预占、循环返工终止。测试使用独立数据库与模拟收费调用；真实模型效果另以小规模、脱敏样例验收，不虚报完成率或 token 精确度。

完成第一批后，系统应能解释并展示“任务做到哪里”；完成第二批后，多个角色才能基于这份状态可靠地交接和继续执行。两者分别验收，不将已存在的四角色提示词流程描述成新增完整多 Agent 平台。
